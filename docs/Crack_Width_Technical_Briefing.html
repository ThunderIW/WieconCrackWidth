Wiecon · Internal Tools

Crack Width Application

A reinforced-concrete crack-width check to EN 1992-1-1 cl. 7.3.4, delivered as a self-contained Windows desktop app. What it does, how it's built, and what's still wrong with it.

What it is, in one breath

The elevator answer

It takes the 16 inputs an engineer already has — section geometry, reinforcement layout, material grades, and the service loads N and M — and returns the characteristic crack width wk, checked against a limit. The answer updates as you type; there is no Calculate button. It saves named cases to a local database so you can compare a wall's base, mid and top in one table, and export any of them to a PDF report.

It runs as a single .exe. No Python install, no browser, no server to start. Double-click and a native window opens.

Architecture

Three layers, each replaceable without touching the others

main_niceGUI.py The whole UI, and the shell. build_ui() declares the element tree; ui.run(native=…) owns the window and the server. One file, one entry point.
WieconTools/ The engine. crack_analyze — pure maths, no UI import, no database. Testable on its own.
models/
DatabaseInteractionTools/ Persistence. SQLModel over SQLite; InteractionFile is the only thing that talks SQL.

The important property: the engine knows nothing about the UI. crack_analyze takes numbers and returns a report_result dataclass with all 22 quantities, not just the answer. That's why the detail view, the PDF report and the database row can all be built from one run, and why the engine can be regression-tested without launching anything.

The front of the stack is deliberately flat. There is no shell module and no page router: ui.run(native=True) is the shell, so the whole app is one screen in one module, reached with no navigation at all. Everything the tool does is on that screen when it opens.

Process and deployment view

Two OS processes, one boundary between them. The server is the parent: ui.run(native=True) starts uvicorn in this process and spawns the pywebview window as a child. Everything below the dotted line is ordinary Python.

The child is spawned by multiprocessing, which on Windows re-imports this module under the name __mp_main__ — which is why the entry guard reads if __name__ in {"__main__", "__mp_main__"} rather than the usual one name. Miss that and a frozen exe relaunches itself forever. multiprocessing.freeze_support() is what makes the spawn work once bundled.

You will see two processes in Task Manager. That is correct, not a leak. Note the port is fixed at 8082, not an OS-assigned free one: if something else holds it, the app will not start.

Frontend architecture

A real element tree with real event handlers — built once, then mutated

The single most important thing to understand: the script does not rerun. build_ui() executes once per client, constructing a tree of Python objects that persist on the server. Every one of them has a JavaScript counterpart in the browser. When a handler mutates an element, NiceGUI sends the delta down a websocket. The tree is built once and then mutated in place for the life of the client — there is no re-execution to design around.

State — where it actually lives

There is no session store. The elements are the state, and inputs is just a dict of references to them.

Nothing is stashed anywhere, and nothing is cached. The Save button keeps no copy of the last result: it re-reads inputs and re-runs the engine, which is cheap and deterministic. That is what guarantees a saved row's inputs and outputs can never disagree — both come from one run, made at the moment you asked for it.

Three rules the layout obeys

The inputs are debounced. Every ui.number carries debounce=300: a field waits 300 ms after the last keystroke before it fires. That is what makes a live verdict tolerable — it follows you as you type, but never flashes a value computed from a half-typed number, and it is why there is no Calculate button to press.

The chip must survive bad input. live_chip() is called on every change, including while a field is empty (ui.number holds None, not 0) or mid-edit. It returns a grey — for both the empty case and any engine exception, silently. The explicit Save path does the opposite: it names the missing fields, because there the user asked for an answer.

The UI must be built inside a root function. ui.run(root=build_ui) takes the function, uncalled. Build the UI at module level instead and NiceGUI drops into "script mode", re-executing sys.argv[0] per client — which in a frozen exe means handing a binary to runpy and dying on source code string cannot contain null bytes.

Backend architecture

One contract in, one dataclass out, seven columns persisted

The data contract

The whole backend is a funnel: 16 inputs split into a section and a load case, the engine returns 22 quantities, and only 7 of them are written to disk.

The 15 dropped fields — x, alpha_e, fctm, hc_eff, k2, esm_minus_ecm, cracked and the rest — are the intermediate workings. A saved case therefore cannot reproduce the full report table as-is. It doesn't need to: because all 16 inputs are stored verbatim and the engine is deterministic, any saved row can be re-run to regenerate every intermediate. That's a deliberate trade, and it's the answer if someone asks why the table is so narrow.

One caveat the diagram can't show: report_result is a mutable dataclass. Nothing currently mutates one, but nothing stops it either.

Persistence

InteractionFile is the entire data-access layer — three methods, and the only place SQL is spoken:

MethodDoesNotes
get_all_result_for_crackWidth_table()SELECT all, newest firstOrdered by created_at DESC
add_new_result_to_crackWidth_table()INSERT one caseSplats **params + 7 result keys; returns the row with its id

StartEngine owns the SQLite engine and creates the schema on construction — create_all emits CREATE TABLE IF NOT EXISTS, so it is safe against a populated database. Every method opens and closes its own Session: short transactions, nothing held open between interactions.

What there is not is any caching of the engine itself. The four call sites each construct InteractionFile() inline, and its __init__ builds a new engine every time — so every save, every delete and every grid refresh re-runs create_all against the database. See defect 6. It is not a correctness problem, and against a local SQLite file it is not a visible one either, but it is the wrong shape, and worth knowing before someone reports it as one.

Why the layering pays off

Because crack_analyze imports neither the UI framework nor anything web-facing, the entire verification section below was produced without launching the app, and still stands without re-running a single calculation. The frontend could be replaced wholesale — a different framework, a different execution model, a different process topology — and these three packages would not notice. The same property means the engine could be lifted into a REST service, a batch job over a spreadsheet of sections, or the next UI, without a single edit.

How the desktop packaging actually works

The part people ask about, because it's the non-obvious bit

NiceGUI is a web server — FastAPI under uvicorn — so a desktop build needs both a window and a server. You do not write the glue between them: native=True makes NiceGUI spawn the pywebview window itself:

CrackWidthNiceGUI.exe            ← parent: uvicorn + the element tree
  └── CrackWidthNiceGUI.exe      ← child:  the pywebview window
      (re-imported as __mp_main__)

One flag covers it — no sentinel argv to parse, no health-check polling, no teardown to write by hand. The same ui.run() call serves both modes, keyed off FROZEN = getattr(sys, "frozen", False): packaged, you get a native window and no reloader; from source, you get a browser tab with hot reload. That branch matters — watchfiles cannot run inside a frozen exe.

Why a window and not a browser tab

The app could simply open at localhost:8082 in Edge — that is exactly what it does in development. It ships as a window because the deliverable is a tool an engineer double-clicks, not a service they navigate to: no browser to keep open, no URL to remember, no tab lost among thirty others, and a taskbar icon that says what it is. pywebview runs real CPython behind WebView2, so nothing about the app changes between the two modes — same server, same element tree, same SQLite file.

The NiceGUI mental model

If you're asked "how does the UI work", this is the answer

The UI is a tree of Python objects that outlives the request. build_ui() runs once per client and never again. After that, handlers fire on events, mutate elements, and NiceGUI ships the diff to the browser over a websocket. It is closer to writing a desktop toolkit than to writing a web page.

The quirks the model does produce are its own: ui.number holds None when cleared (not 0), so every read path has to tolerate it; AG Grid's no-rows overlay does not lift itself when rowData is filled live, so refresh_saved_cases() toggles it by hand; and replacing rowData drops the selection without reliably firing selectionChanged, so the action buttons have to be hidden manually or they linger, still offering to delete rows that are no longer selected.

The calculation

EN 1992-1-1 cl. 7.3.4 — nine steps, in fixed order

Steps 4 and 7 were corrected on 17 July 2026 to fix defect 3. The nine steps, and their order, are otherwise as first written.

  1. Steel areasAs per metre from bar diameter and spacing, both faces.
  2. Material propertiesfctm, Ec, creep-adjusted Ec,eff, modular ratio αe. Two branches at fck = 50 MPa.
  3. Cracking checkσct = N/A + M/W against fctm. Reported — but see defect 4.
  4. Steel stressThe hard one. Bisects for the neutral axis x, then σs. Splits into "N+M" and "pure-tension" modes.
  5. Effective tension areahc,eff, Ac,eff, ρp,eff, and the strain coefficient k₂.
  6. Mean strainεsm − εcm, with the code's 0.6σs/Es floor.
  7. Crack spacingsr,max — Eq 7.11 for close bars, Eq 7.14 when spacing exceeds 5(c + ø/2).
  8. Crack widthwk = sr,max × (εsm − εcm).
  9. Verdictwk ≤ wmax.

Defects — four fixed, two open

Be honest about these when asked. The ones that mattered are closed; the rest you should be able to name.

1. Pure bending returned zero crack width FIXED

With N = 0 the solver fell into pure-tension mode and computed σs = N / As = 0, so wk = 0.000 mm and the check passed. A pure-bending member — the most common case there is — was silently reported as safe.

Cause: the neutral-axis solve was formulated around the load eccentricity M/N, undefined at N = 0. The bisection failed to bracket and degraded to the tension branch.

before N=0, M=250 → σ_s = 0.0 MPa, w_k = 0.000 mm, PASS after N=0, M=250 → σ_s = 415.1 MPa, w_k = 0.724 mm, FAIL

2. Compression yielded a negative crack width FIXED

Compressive N produced σs = −87.3 MPa and wk = −0.163 mm — a negative crack width, which then satisfied the ≤ wmax test. The form places no lower bound on N, so it was reachable.

Now the section is solved properly under compression (the neutral axis rises, steel stress drops), and where the steel goes into compression there is no crack to measure.

before N=-300, M=116 → σ_s = -87.3 MPa, w_k = -0.163 mm after N=-300, M=116 → σ_s = +87.3 MPa, w_k = 0.144 mm

The fix, in one line APPLIED

Both defects were the same root cause: dividing by N. The equilibrium condition Mf(x)/Pf(x) = h/2 + M/N was restated as

F(x) = M·Pf(x) + N·Qf(x) = 0

— algebraically identical wherever the old form was valid, but defined at N = 0 (where it reduces to Pf(x) = 0, the textbook pure-bending neutral-axis condition) and correctly signed for N < 0. A negative σs now yields wk = 0 rather than a negative crack width. All seven benchmark quantities still reproduce exactly.

5. Deleting a missing row raised FIXED

delete_results_from_crackWidth_table passed None to session.delete() when an id wasn't found, raising UnmappedInstanceError, and counted it as deleted regardless. It now looks the row up first, skips a miss without counting it, and returns the true number removed — which is what the "Deleted n Files" toast reports. It was only ever reachable by deleting a row twice, which the UI does not offer.

3. The creep coefficient moved wk the wrong way FIXED

Creep should increase crack width. Setting φ = 2.0 decreased it, 0.678 → 0.670, and then φ stopped doing anything at all: every value from 0.5 upward returned exactly 0.670. The neutral axis never moved off 25.121 mm and σs never moved off 395.658 MPa, whatever φ was set to.

Two faults, one symptom. Step 4 solved the section with the raw Ec, so φ never reached the cracked-section analysis. Step 7 then fed it the creep-adjusted αe — but Eq 7.9 defines αe as Es/Ecm, the short-term secant modulus. Creep enters Eq 7.9 through kt (0.4 sustained / 0.6 instantaneous) and through σs, not through αe. So the only path φ had was a term that subtracts: a rising αe inflates (1 + αeρp,eff), shrinking the strain until it hit the 0.6σs/Es floor and pinned there.

Now step 4 solves on Ec,eff = Ecm/(1 + φ) and step 7 uses the Eq 7.9 ratio. Creep reaches the section, deepens the neutral axis, and raises both σs and the strain.

before phi 0 -> 2: x = 25.121 -> 25.121 mm, sigma_s = 395.66 -> 395.66 MPa, w_k = 0.678 -> 0.670 (fell, then inert) after phi 0 -> 2: x = 25.121 -> 35.044 mm, sigma_s = 395.66 -> 396.98 MPa, w_k = 0.678 -> 0.681 (rises)

It did not move the benchmark. The old note here assumed it would, and that was wrong: at φ = 0, Ec,eff = Ecm and Es/Ecm = Es/Ec,eff, so both edits are algebraically inert. Every φ = 0 result in this document is bit-identical across the fix — the benchmark, the load sweep, and every parameter row but creep. There was never a decision to make about which was authoritative; the code answers it.

What it does not buy you, and worth saying before someone reports it as a bug: wk still is not monotonic in φ for every section. wk = sr,max × ε, and EN 1992-1-1 ties sr,max to the neutral axis — Eq 7.14 is 1.3(h − x) outright, and Eq 7.11 runs through ρp,eff, which hc,eff = min(2.5(h−d), (h−x)/3, h/2) sets. Creep deepens x, so both shrink the spacing. Across 600 randomised sections the strain now rises with φ every time, but on sections where the spacing loss outruns the strain gain — deep members with widely spaced bars, on Eq 7.14 — wk still eases off, by up to 10% at φ = 3. That is the code's geometry, not this implementation, and "fixing" it would mean departing from EN 1992-1-1.

4. The cracked flag is computed and never used OPEN — AND ODD

Step 3 tests σct ≥ fctm and stores the result as cracked, which nothing reads. The obvious fix — skip the check when uncracked — cannot be applied, because by that test the Wadi benchmark is itself uncracked (σct = 3.53 < fctm = 4.07) and yet the reference tool computes wk = 0.678 for it regardless.

So either the flag's threshold is wrong, or the reference tool deliberately checks uncracked sections too. Worth resolving before anyone leans on that column — it's the one open question about the engine's intent.

6. A fresh database engine per interaction OPEN — MINOR

Each of the four call sites constructs InteractionFile() inline, and its __init__ builds a StartEngine() — a new SQLAlchemy engine, plus a create_all() round-trip to the database — on every save, every delete and every grid refresh. Nothing holds a single engine for the life of the app.

Harmless in practice against a local SQLite file with one user, which is why it is filed as minor rather than fixed. It is still the wrong shape: one module-level instance would do. Name it before someone else finds it.

Packaging: the things that broke

Worth knowing — each one cost a build cycle, and each will bite again

Downloads silently cancelled

pywebview ships ALLOW_DOWNLOADS = False, and the WebView2 backend cancels the download outright — no error, no console output, nothing reaching Python. The PDF export button looks broken but isn't. The fix has to go through app.native.settings['ALLOW_DOWNLOADS'] = True so it reaches the pywebview subprocess; setting it on webview.settings in the parent would not, because the window lives in the child.

The database moves when frozen

A PyInstaller build unpacks to sys._MEIPASS, a temp directory Windows wipes on exit, so the database cannot live there. It is written to data\ beside sys.executable instead — the real on-disk location of the exe, not the temp unpack — which makes the app portable: copy the folder to a USB stick and the saved cases travel with it. Source checkouts still use database\.

The schema was never created FIXED

StartEngine.create_table() existed but was called from nowhere; the dev database happened to have the table already, so it worked on exactly one machine. Called from __init__ since, and create_all is idempotent. Still true today — if anything it now runs rather too often (defect 6).

Local modules silently missing from the bundle AVOIDED

collect_submodules() runs in an isolated subprocess without your project root on sys.path, and returns an empty list for local, non-installed packages — no warning, nothing bundled, and a ModuleNotFoundError at runtime. CrackWidthNiceGUI.spec avoids it: local modules are picked up by following the imports from main_niceGUI.py, and collect_all() is used only for the three third-party packages that carry data files or hidden imports — nicegui, webview and fpdf. Recorded because the trap is still there if anyone reaches for collect_submodules again.

A frozen exe cannot re-execute its own script NEW

NiceGUI's default "script mode" re-runs sys.argv[0] per client. In a frozen build sys.argv[0] is the exe, so runpy tries to parse a binary as Python and dies on source code string cannot contain null bytes. Passing root=build_ui — the function, uncalled — sidesteps the re-execution entirely. This is why all UI construction lives inside one function rather than at module level, and it is not a style choice.

Build and run

From the project root

# the engine's regression suite (pins the benchmark, guards defect 3)

The spec builds windowed (console=False), so a traceback in the packaged app goes nowhere you can see — run from source when you need one. datas=[('docs','docs')] bundles the reference diagram, the logos, the user guide and the changelog; the two documents are also copied to the top level of the dist folder, because _internal\ is not a place users look.

Port 8082 is hard-coded in ui.run(). Nothing negotiates a free one, so a stale instance holding the port will stop the next launch.

Tests

tests/test_creep.py is the only suite so far, and it covers the engine rather than the UI — which is the layering paying off again: no window, no server, no database, just the maths. It pins all six benchmark quantities and asserts the invariant the creep fix guarantees, that φ never reduces steel stress or mean strain, across 600 randomised sections. Reverting either half of that fix turns 370 of its 949 cases red, so it is worth keeping green.
